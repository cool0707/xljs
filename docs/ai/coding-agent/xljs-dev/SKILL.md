# xljs のスクリプトの開発（開発モードを使わないとき）

xljs には AI チャットと並べて使う「開発モード」（`xljs dev`）がある。開発モードは、AI の回答の取り込み・前の版への戻し・実行とエラーの報告・フォームのプレビュー・テスト・exe の作成を利用者の代わりに行う。
このスキルは、ファイルを直接読み書きしコマンドを実行できるあなた（コーディングエージェント）が、**同じことを自分で行う**ための決まり。
xljs の API・スクリプトの書き方の決まり（ツールかアプリかを決める、画面はフォームで作る、入力チェック、新しいファイルに保存など）は `prompt.md` と `reference.md`（スキルなら `xljs-reference`・`xljs-app-design` など）に従う。ここに書くのは進め方だけ。

チャットとの違い:

- 回答の決まりの「完成した 1 ファイルをコードブロックで出す」「使い方を 2〜3 行で書く」は、**ファイルを直接書き換える**・**終わったら使い方と確かめたことを短く報告する**に読み替える。
- 利用者はプログラミングに詳しくない。コマンドの出力をそのまま見せず、何が起きて何を直したかを日本語で短く伝える。

## 0. 環境を確かめる

- xljs は Windows の実行ファイル。コンソールに出力が出るのは **`xljsc.exe`**（コンソール版。配布 zip に `xljs.exe` と並んで入っている）。`xljs.exe`（GUI 版）でも動くが、出力が見えないことがあるので、確かめるときは `xljsc` を使う。見つからなければ場所を利用者に聞く（PATH にないことが多い）。以下 `xljsc` と書く。
- 型定義がなければ、スクリプトのフォルダで `xljsc init` を実行する（`xljs.d.ts` と `jsconfig.json` ができる）。**API があるか迷ったら `xljs.d.ts` を検索する**。d.ts にない関数・オプションは使わない。
- スクリプトの拡張子: 利用者に渡すのは `.xljs`（中身は TypeScript の構文）。開発中は `.js` / `.ts` でもよい。既存のファイルの拡張子は変えない。

## 1. 作り始める前に（新規作成）

開発モードの新規作成ウィザードが聞くことを、足りなければ利用者に聞く（推測できるものは仮定を書いて進める）:

- **作るもの**: 入力して実行するツール（集計・変換など、1 回の実行で終わる）／開いたまま使うアプリ（一覧・検索・登録・更新など。データを持ち越す、機能が複数ある）。依頼の内容から決める。
- **形式**: フォームアプリ（既定。画面は `ui.form`、機能ごとに画面を分けるなら `ui.forms`。ツールもアプリも作れる）／カスタムアプリ（`@mode app` と HTML。表のセルに打ち込みながら行を増やす明細、標準の部品にない見た目・操作が要るとき）／画面なし（タスクスケジューラーや他のアプリから自動実行）。
- **使う人**: 自分だけ／共有フォルダに置いて複数の人で。複数なら書き込むデータは SQLite の共有モードで場所を固定、実行している人の氏名・所属は入力させず `ad.me()`。
- **データ**: 保存しない／次回に持ち越す（SQLite）。
- **入力と出力の形**: シート名・見出しの行・列名、出力のファイル形式と保存先。**入力ファイルがあれば、推測せずに中身を読んで確かめる**（下の「ブックの中身を見る」）。

Excel マクロの移植なら、ブックからマクロとシートの仕組みを書き出して読む（スキル `xljs-vba-port` に従う）:

```
xljsc vba --all 売上集計.xlsm -o 売上集計_xljs.md
```

`--all` はマクロ・数式・入力規則・名前の定義・条件付き書式・グラフ・表の列の特徴。`.xls` はシートを読めない（マクロは読める）。

## 2. 書き換える前に履歴を残す

開発モードは、ファイルを置き換える前の内容を残し、利用者がいつでも前の版に戻せるようにしている。同じことをする:

- フォルダが Git の管理下なら、書き換える前にコミットする（利用者がコミットを望まないなら次の方法）。
- そうでなければ、書き換える前のファイルを `.xljs/versions/<スクリプトのフォルダからの相対パス>/` に `0001.js`・`0002.js`…（元の拡張子。番号は続き）として写し、同じフォルダの `log.json`（配列）に `{"n": 番号, "time": "2026-04-10 15:30:00", "note": "何のための変更か"}` を足す。この形にすると、利用者が開発モードを開いたときに［履歴］から戻せる。
- **利用者が自分で直したところを元に戻さない。** 書き換える前に必ず今のファイルを読み直す（前に読んだ内容をもとに書かない）。

## 3. 確かめる（画面を出さずに実行する）

書いたら、利用者に渡す前に必ず次を行う。

1. **構文と import**: `xljsc check 集計.xljs`（`OK` なら成功。失敗は `ファイル:行:列` 付き）。
2. **型**（Node と TypeScript が使えるときだけ）: `xljs init` のフォルダで `npx -p typescript tsc -p jsconfig.json`。`.xljs` は tsc が読まないので、`.ts` に写して確かめる（写しは終わったら消す）。
3. **モックの UI で実行**: ダイアログ・フォームに答えるファイルを作業用の場所に作り、画面を出さずに最後まで動かす。

```
xljsc --ui=mock --ui-answers=answers.json --lang=ja 集計.xljs [引数...]
```

answers.json（キーはどれも省略できる。種類ごとに前から順に使い、尽きると「キャンセル」）:

```json
{
  "form": [{ "src": "data/売上", "out": "out.xlsx", "from": "2026-04-01", "count": 3 }],
  "confirm": [true],
  "prompt": ["2026-04"],
  "showOpenFilePicker": [["data/4月.xlsx"]],
  "showSaveFilePicker": ["out.xlsx"],
  "showDirectoryPicker": ["data"],
  "table": [[0, 2]]
}
```

- `form` はボタンを 1 回押すごとに、既定値から**変える項目だけ**（項目の `name` がキー。グループの中の項目もそのまま並べる）。ファイル・フォルダはパスの文字列、日付は `"2026-04-01"`、`null` は閉じる。primary のボタン（なければ先頭のボタン）以外を押すなら `"$button": "ボタンの表示名"`（番号も可）、編集できる表のセルは `"$cells": { "項目名": [[行, "列名", 値]] }`。`table` は選んだ行の番号。アプリモードの画面の操作は `"app": [[{ "invoke": "関数名", "args": [...] }, { "close": true }]]`。
- パスはカレントフォルダからの相対パス。**入力のファイルは写しを使い、出力は作業用のフォルダに出す**（利用者のファイルを上書きしない）。テスト用のデータがなければ、小さいサンプルを作業用のフォルダに作る（見出しの形は利用者の説明どおりに）。
- 標準出力に `[mock] form("売上集計") -> {...}` のように応答が出る。**`[mock] form error: 項目: 文面`** は入力チェックで戻されたこと。入力チェックを確かめるときは、わざと誤った値を答えて、このエラーが出ることを見る。
- 環境変数 `XLJS_DEV=1` を付けると、`fs.remove` が多くのファイルを消す前に `confirm` で尋ねる（モックでは `confirm` の応答がなければ消さずに止まる）。消す処理のあるスクリプトは付けて試す。
- **無限ループに備えて、コマンドには時間の上限を付ける**（モックの UI では xljs の監視は働かない）。止まらなければ、ループの終了条件を疑う。
- 終了コード: 0 正常、1 エラー（`exit(1)` も）、124 応答しないので中止、130 利用者が停止キーで中止。キャンセルされたフォームは 0。

### エラーの読み方

エラーは標準エラー出力の**最後の、インデントのない行から後ろ**（エラーの文面とスタック）。スタックは元のファイルの `ファイル:行:列` になっている（`.ts`・`.xljs` の行番号のまま）。最初に出てくるスクリプトのファイル（`node_modules` 以外）の行がエラーの場所。そこを読んで原因を直し、もう一度 3 を通す。
利用者がエラーダイアログの文面を貼ってきたときも同じように読む。

### ブックの中身を見る

入力ファイルの形や、出力した xlsx の中身を確かめるには、小さなスクリプトを作業用のフォルダに書いて実行する（利用者のスクリプトのフォルダには置かない）:

```js
// dump.js: xljsc dump.js ブック.xlsx
const book = excel.open(xljs.args[0]);
for (const sheet of book.sheets) {
  console.log(`# ${sheet.name}`);
  for (const r of sheet.toRowObjects().slice(0, 10)) console.log(JSON.stringify(r));
}
```

## 4. 画面（フォーム・アプリ）の見た目

あなたは画面を見られない。モックで動きと入力チェックは確かめられるが、配置・見た目は確かめられない。

- 見た目に関わる変更をしたら、利用者に**実際に開いてもらう**（`xljs.exe` へのドラッグ＆ドロップ、`.xljs` のダブルクリック、または開発モードの［フォーム］タブのプレビュー）。見てほしいところを具体的に書く。
- 利用者が「このボタンを右に」のように画面の要素で頼んできたら、フォームの定義（`fields` の項目、`ui/*.html` の要素）のどれのことかを確かめてから直す。

## 5. テスト（`.xljs/tests`）

スクリプトのフォルダに `.xljs/tests/` があれば、利用者が「正しい」と認めた実行の記録がある（記録・再生型のテスト）。

- **スクリプトを変えたら毎回再生する**: `xljsc test 集計.xljs`（フォルダを渡すと全部）。終了コード 1 は失敗か問題。
- 失敗の差分は `-` が以前の正しい結果、`+` が今の結果（`form`・`field` はフォームの表示、`out` はログ、`ファイル名 シート!セル` は出力ファイルのセル）。**利用者が頼んでいない違いなら、スクリプトのほうを直して以前と同じ結果に戻す。**
- 頼まれた変更で結果が変わったのなら、それは失敗ではない。利用者に違いを伝え、確かめてもらって承認してもらう（`xljs test --approve 集計.xljs`。開発モードの「テスト」タブでもできる）。
- **`.xljs/tests` の中身（`case.json`・`expected/`・`input/`）を自分で作らない・書き換えない・`--approve` を自分で実行しない。** 正解を決めるのは結果を見られる利用者だけ。ケースは利用者が `xljs test --record <ケース名> 集計.xljs` で本物の画面を操作して作る（必要なら勧める）。
- `problem`（記録にない問い合わせ・フォームにない項目など）は、フォームの項目名や問い合わせの順を変えたときに出る。意図した変更なら利用者に記録し直してもらう。

## 6. 渡す

- 利用者へは、何をしたか・どう使うか（ドラッグ＆ドロップするもの、出てくる画面、出力の場所）・確かめたこと（モックで実行した、テストが通った）・利用者に見てほしいこと、を短く伝える。
- 1 つの exe にして配るなら: `xljsc pack 集計.xljs -o 集計.exe`（メタデータの警告が出たら直す）。
- `.xljs/` には履歴・テスト・開発モードの設定が入る。消さない。作業用のファイル（answers.json、dump.js、出力の試し）はスクリプトのフォルダに残さない。
